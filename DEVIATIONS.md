# Deviations from SPEC.md

Where SPEC.md turned out to conflict with reality or with a hard constraint, the code follows
reality and the change is logged here. Evidence is in `REALITY_REPORT.md`.

| # | Spec says | We do | Why |
|---|---|---|---|
| 1 | `Verdict` is a frozen dataclass with `.model_dump()` | Frozen pydantic `BaseModel` | `.model_dump()` is a pydantic method; dataclasses don't have it. Matches the SDK's own frozen answer models. |
| 2 | Runtime dep `pydantic>=2` | `pydantic>=2.12` | `typesafe-sdk` 0.7.1 requires it. |
| 3 | SDK package unnamed | `typesafe-sdk>=0.7.1,<0.8` | The official package. It had breaking changes in both 0.6 and 0.7, so we pin the minor version. `typesafe-ai` on PyPI is an unofficial third-party shim and is not used. |
| 4 | Every primitive has three fields incl. `confidence` | Noul answers have only `noul`; `JevAnswer.confidence` is optional | Real API shape. A noul's probability is used as its risk directly. |
| 5 | Flat "$0.0004 per check" | Cost is computed per call from `usage.input_tokens` × $0.042/1M | $0.0004 implies about 9.5k tokens per check; real guard checks are about 300–1,500 tokens. Falls back to a chars/4 estimate if usage isn't reported. |
| 6 | (implicit) SDK client built with `Guard(...)` | Built lazily on the first check | Since 0.7.1 the SDK validates the key in its constructor. Lazy creation means `Guard(...)`, `policy show` and `validate` work without a key. |
| 7 | Nightly GitHub Action runs the golden eval against real Jev (~$0.20/run) | Removed; the eval runs locally only, on demand | Owner requirement: no API key is ever stored in CI, so the open-source repo can never bill the maintainer. |
| 8 | Integration tests gated on `TYPESAFE_API_KEY` | Gated on `TYPESAFE_API_KEY` **and** `JEV_GUARD_ALLOW_LIVE=1`, plus a 200k-token budget per session | Having a key in your shell for other reasons shouldn't be enough to spend money. |
| 9 | Layout has no module for `Guard` | Added `src/jev_guard/guard.py` | `guards/input_guard.py` and `guards/output_guard.py` hold the per-stage request builders; the public class needed its own home. |
| 10 | Section 5 rules ("review if X > t") vs Section 6 ("medium/low don't drive action alone") | Single-question review rules are `high` severity with weight 2.0 and `review_threshold` 1.0 | So one fired `high` question means review and several can block (when a policy sets `block_threshold`). Rejected alternative: summing raw probabilities, because one strong signal gets diluted when a policy has 5+ questions. |
| 11 | (unspecified) Behaviour when Jev is down | Checks raise `JevAPIError` | Rejected fail-open (it silently disables safety) and fail-closed (a Jev outage takes the app down). The app decides. |
| 13 | Section 5: "`from_builtin` and `from_yaml` produce equivalent behavior on the golden dataset" | Until Phase 5: identical `model_dump()`, and identical aggregation on 300 seeded random answer sets per policy and stage. A drift test fails if a YAML twin goes stale | The golden dataset doesn't exist until Phase 5. Random answers cover threshold edges more densely than 100 real samples would. |
| 14 | (unspecified) YAML format | Keys mirror `Policy` fields; `extends: <builtin>` merges per question and `null` removes an inherited question | Lets Marcus change one threshold without copying 150 lines. The builtin twins are still complete, standalone files. |
| 15 | Section 5 `rag`: "fall back to general behavior on the output" | New `context_fallback` policy field (rag sets `general`). Guard logs a warning and appends a reason noting the fallback | Keeps the behavior expressible in YAML instead of hardcoding it in a Python subclass. |
| 16 | Section 5 lists questions but not stages or severities for some | `support_agent`: `frustration_level` and `should_escalate_to_human` run on **input**, and `contains_refund_promise` is `high` (review). `coding_agent`: `network_egress_intent == write` and `attempts_privilege_escalation` are `high`, and `block_threshold` is 3.0. `rag`: grounded, hallucination and contradiction are `high` with `block_threshold` 3.0; citation is `low` and context-sufficiency is `medium` | Spec gives no rule for these. Privilege escalation isn't critical because dev tools use sudo legitimately; contradiction isn't critical because one uncertain signal shouldn't hard-block a bank's answer. `coding_agent_prod.yaml` shows the stricter setup. |
| 17 | `QuestionSpec.kind` (internal name) | `type` | Matches the Jev wire format and the Section 7 linter message ("unknown question type"). |
| 18 | (unspecified) What integrations do on `block` | `@guarded` returns the policy's safe reply string. `wrap_openai` / `wrap_anthropic` / the LangChain handler raise `GuardBlockedError` (carries `.verdict` and `.suggested_response`) | A decorated `prompt -> str` function can return a safe string transparently. Rejected for the client wrappers: fabricating a `ChatCompletion` / `Message`, because callers reading `id` or `usage` would get made-up data. |
| 19 | "`@guarded` decorator + monkey-patch helper" | Integrations are duck-typed and don't import `openai` / `anthropic`. `wrap_openai` covers `chat.completions.create` and `responses.create`, sync and async. With `stream=True` the wrappers check input only and log a warning until Phase 6 streaming lands | Installing jev-guard never pulls in an LLM SDK. The Responses API is OpenAI's current primary API, so skipping it would miss many users. |
| 20 | LangChain in `[langchain]` extra | Also in `[dev]` extra | Needed to type-check and test the callback in CI. Users still only get it via `[langchain]`. |
| 21 | Entry point `jev_guard.cli:app`; Typer in `[cli]` extra; Section 15 "`pip install -e .` → `jev-guard --help` works" | Entry point `jev_guard.cli:main`, a shim that loads the Typer app from `_cli_app.py` or prints `pip install "jev-guard[cli]"`. Also `python -m jev_guard` | The spec's items conflict: without the extra, an entry point pointing straight at a Typer app crashes with an ImportError. Rejected making Typer and Rich core deps: ~3 MB for library-only users. |
| 22 | (unspecified) Cost safety for `scan` | `scan` estimates cost locally first and refuses above `--max-cost` (default $1.00). It stops mid-run at the cap (failed calls release their reservation), and `--dry-run` makes no calls | A mistyped path to a large log shouldn't silently spend money. |
| 23 | `scan` / `check` flags | Added `scan --dry-run --max-cost --concurrency` and `check --output --context --json --fail-on`; `check` exits 3 when `--fail-on` triggers | Shell scripts need a machine-readable result. A block isn't an error, so it doesn't exit 1. |
| 24 | Section 7 `eval` command in Phase 4 | Lands in Phase 5 with the golden runner and dataset | It has nothing to run until then. |
| 25 | Layout | Added `eval/logs.py` (format detection), `eval/scan.py` (batch engine), `eval/metrics.py` (P/R/F1 shared by scan and eval) | Keeps `report.py` about rendering only. |
| 26 | Langfuse / Arize "detect by header" | Detected from the first record's keys (`projectId`/`traceId`/`sessionId` → Langfuse; `attributes.*`/`context.span_id` → Arize OpenInference) | Extraction is best-effort: both vendors' export shapes vary by SDK version. Not yet verified against real exports from either. |
| 12 | Choice rule "`intent == malicious` AND its confidence > 0.8" | Implemented exactly; the choice's *risk* for `confidence` is the summed probability of its flagged labels | Keeps `confidence` informative when Jev picks `borderline` but still puts real weight on `malicious`. |
